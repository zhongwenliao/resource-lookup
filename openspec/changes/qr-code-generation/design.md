# 设计：二维码生成（生成端能力规格化）

## Context

生成端全部逻辑集中在 `src/views/QcLabel.vue`（约 1050 行单文件组件）：Excel 解析 → 列识别 → 码值组装 → 批量生成 → 打印/BTXML 输出。产品决策：二维码内容只保留编码规则模式（明文文本与网页链接模式移除）；编码规则码仅含拼码配置信息（项目/组件/阶段/颜色/供方/原材/阳极/年/月/日/流水码），不含记录明细（序号/时间/判定/测量值），扫码回查记录需依赖生成时落库的「规则码 ↔ 记录」关联。编码规则常量（阶段/颜色/月份映射、补零函数）与归一化函数内聚在该组件的 `<script>` 顶部。进行中的 `qr-traceability-lookup` 变更（查询端）计划从该组件抽取共享规则模块（其任务 1.1/1.2），且其中引用的 `STAGE_OPTIONS`/`COLOR_OPTIONS` 已在近期调整中更名为 `STAGE_CODE_MAP`/`COLOR_CODE_MAP` + `normalizeStage`/`normalizeColor`，任务清单已过时。本变更把生成端行为固化为规格并完成模块抽取，作为两端共享规则的落地载体。导入的表格数据目前仅存于组件内存，页面刷新即失；项目当前无任何本地存储设施（无 IndexedDB/localStorage 使用，依赖中无存储库）。

## Goals / Non-Goals

**Goals:**

- 生成端行为以规格固化，作为后续演进的验收基准
- 抽取 `src/common/qc-code-rules.js` 共享规则模块，生成端改为引用，行为零变化
- 与 `qr-traceability-lookup` 变更的任务清单对齐，避免重复抽取与规则漂移
- 导入批次落前端数据库（IndexedDB）本地持久化，支持历史批次查看/载入/删除
- 二维码内容收窄为编码规则单一模式，并建立规则码与记录的关联持久化，支撑查询端按码回查

**Non-Goals:**

- 除「导入数据本地持久化」「规则码与记录关联持久化」「内容模式收窄为编码规则」外不新增/修改任何用户可见行为（含近期已实施的直接输入、年份/月份自动/手动调整——它们随本次一并纳入规格，但代码不再改动）
- 不实现查询端解析页面（属 `qr-traceability-lookup`）
- 不做跨设备同步与服务端存储，不持久化生成的二维码图片（可再生成）
- 不引入新依赖、不改构建与打包流程

## Decisions

### D1：共享规则模块 `src/common/qc-code-rules.js`

迁出内容：`STAGE_CODE_MAP`、`COLOR_CODE_MAP`、`MONTH_CODES`、`normalizeStage`、`normalizeColor`、`pad2`、`pad5`，并新增 `encodeRecordToBase64url(record, model)`（生成端编码）与 `splitRuleCode(code)`（规则码从右向左拆段校验，查询端消费）。`QcLabel.vue` 改为 import 引用。base64url 编解码导出保留：生成端移除网页链接模式后不再调用，但查询端解析历史网页链接码（`static/qr-view.html` 生态）仍需 `decodeRecordFromBase64url`。

- 备选：两端各自维护一份规则 → 否决，规则漂移正是本变更动机；单文件组件继续内聚 → 否决，查询端无法复用。

### D2：阶段/颜色采用「宽松归一化」而非严格校验

直接填码值（`3/4/5/6/7`、`Q/Y`）原样使用；填已知名称（`V3` 等、`锖色/银色`）自动转码；其余输入原样保留、不报错。

- 理由：编码规则允许留空由供方后补，且可能存在词表外的自定义码值；严格白名单会阻断合法场景。
- 备选：枚举下拉框严格校验 → 否决，正是用户要求改掉的形式；未知输入报错 → 否决，与「供方后补」流程冲突。
- 兜底：码样例实时预览让用户在生成前核对最终码值。

### D3：年份/月份与日期三段解耦

Y（年份末位）与 M（月份码）各自独立「自动取当前 / 手动」；DD（两位日期）独立选择「取记录检测时间 / 手动指定」，来源取不到回退当天。三者互不联动。

- 理由：二阳日期与记录检测时间可能跨月/跨年，Y/M 必须能脱离记录时间手动指定；拆成三段独立控制最直观。
- 备选：单一「日期来源」同时决定 Y/M/DD → 否决，无法表达「日期取二阳但年月取当前」这类组合。

### D4：批量生成保持「非响应式缓存 + 分批让出主线程」

二维码 dataURL 缓存 `qrStore` 挂在 `this` 上（不放 `data`，避免上千条的响应式开销）；每生成 20 条刷新进度并 `setTimeout(0)` 让出主线程。

- 备选：Web Worker 生成 → 否决，`qrcode` 库同步 API 已够用，Worker 引入通信复杂度收益低。

### D5：打印走「独立文档 + 隐藏 iframe」

打印 HTML（含 `@page` 尺寸声明）写入隐藏 iframe 的独立文档，图片解码后触发 `print()`。三类排版分支：标签纸每页一枚、小票纸连续密集平铺、A4 每页 24 枚带裁切线。

- 理由：`@page` 只在独立文档中生效；iframe 方案浏览器与 Electron 渲染进程通用。

### D6：BTXML 与浏览器打印共用同一码值组装与校验路径

两者都经同一「模式校验 → 码值组装」入口取值，保证 BarTender 打印内容与浏览器打印逐字一致。

### D7：与 `qr-traceability-lookup` 的协同边界

本变更承接共享模块抽取（该变更任务 1.1 的迁移部分 + 1.2 的解码/拆段函数）；apply 本变更后需同步改写该变更任务清单：1.1 改为「引用已落地的 `qc-code-rules.js`」、1.2 的 `splitRuleCode`/`decodeRecordFromBase64url` 改为「复用共享模块导出」，并修正其中 `STAGE_OPTIONS`/`COLOR_OPTIONS` 的过时名称。

### D8：导入批次持久化选型 IndexedDB + 轻封装 `src/common/qc-db.js`

数据库 `qc-label-db`，对象仓库 `import-batches`（keyPath `id` 自增，`importedAt` 索引），批次结构 `{id, fileName, model, importedAt, stats, records}`——只存源记录明细与统计，不存二维码 dataURL（可再生成，避免体积膨胀）。解析成功自动写入；判定列改选后按当前批次 `id` 更新。

- 备选 localStorage → 否决，5MB 配额且同步 API 阻塞主线程，数千条测量值记录易超限；主进程 SQLite（better-sqlite3）→ 否决，原生模块需重编译且浏览器模式不可用，破坏双端一致；localForage → 否决，需求仅单仓库 CRUD，轻封装即可，避免新增依赖。
- 降级：打开/写入失败（隐私模式、配额不足）向上返回错误，页面提示但解析结果仍可用于本次生成。

### D9：规则码与记录关联采用「记录内嵌 ruleCode + 遍历检索」

批次记录明细每条内嵌 `ruleCode` 字段（批量生成完成时按生成结果批量回写，重新生成时覆盖更新）；`qc-db.js` 新增 `findByRuleCode(code)`：遍历各批次记录匹配规则码，返回命中记录与所属批次摘要。查询端扫码后先拆段展示，再调用该接口回查记录。

- 备选：独立规则码索引仓库（`rule-code-index`）→ 否决，与批次记录双写需维护一致性、删除批次需级联清理，单机数据量（数千条 × 若干批次）遍历匹配成本可接受；仅靠流水码与生成参数反推记录 → 否决，流水码跨批次重置会撞码，无法唯一定位。
- 未命中语义：规则码检索不到关联记录时仅展示拆段含义并提示（如标签先于数据入库、配置变更后重新生成导致码值变化），不视为错误。

## Risks / Trade-offs

- [抽取常量时引入行为回归] → 验收要求：同一条 OK 记录在重构前后三种模式码值逐字对比相同；`npm run build` 通过
- [两个变更并行实施产生冲突] → 本变更只做迁出不改行为，冲突面小；任务清单对齐后查询端 apply 直接复用共享模块
- [宽松归一化放行未知阶段/颜色输入，码值可能超长或含非常规字符] → 有意取舍（D2）；码样例实时预览 + 生成前人工核对兜底
- [月份码手动输入不校验合法性（如填「13」）] → 与宽松策略一致，原样进码；样例预览暴露问题，不在生成端强行拦截
- [隐私模式/配额不足导致 IndexedDB 写入失败] → 降级为仅内存使用并提示，不阻断解析与生成（D8）
- [历史批次累积占用本地空间] → 只存源记录不存二维码图片；批次可手动删除
- [重新生成导致规则码变化，已贴出标签扫码查不到新库中的旧码] → 记录仅保留最新生成结果（覆盖更新）；查询端未命中时明确提示，不误报
- [移除明文/网页链接模式影响既有使用习惯] → 产品决策收窄；查询端保留对历史明文/链接码的解析能力，已产出的码仍可解析

## Migration Plan

纯前端变更，无既有数据迁移（IndexedDB 存储为全新增量）。实施顺序：先落 `qc-code-rules.js` 与 `qc-db.js` 并让 `QcLabel.vue` 改引用 → 移除明文/网页链接模式入口并落规则码关联持久化 → 构建通过 → 编码规则码值对比回归 + 持久化场景核对 → 同步修订 `qr-traceability-lookup` 任务清单（含新增关联查询任务）。回滚：还原 `QcLabel.vue` 引用并删除新模块即可；已入库的历史批次数据保留在 IndexedDB 中，不影响应用运行。
